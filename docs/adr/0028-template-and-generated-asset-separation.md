# ADR-0028: 開発用 → 公開用 → 生成先の資産分離は `publish` / `generate` の2軸で宣言し、両導線の除外をそこから導出する

- **Status:** Accepted
- **Date:** 2026-07-31
- **Deciders:** itouhi
- **Audience:** publish
- **Related:** [Epic #698](https://github.com/iwata-jawsug-jp/devcon/issues/698)（#699〜#704）、
  提案書（PR #697）、
  [ADR-0010](0010-adopt-copier-for-scaffold-cli.md)（copier 採用）、
  [ADR-0011](0011-scaffold-template-in-place.md)（in-place テンプレート化）、
  [ADR-0001](0001-record-architecture-decisions.md)（Accepted な ADR は書き換えない）、#287、#298、#515

> **Audience 表記について:** 本 ADR で導入する分類（[Decision](#decision) の D1）を本 ADR 自身に適用している。
> `publish` のみ＝公開用リポジトリまでは出すが、copier 生成先には出さない。他の ADR への一括付与は #704。

## Context

本リポジトリの資産は、2段の導線を通って絞り込まれる。

```
[開発用] iwata-jawsug-jp/devcon
   │  publish.yml → publish-to-public.sh（EXCLUDES / ブロック除外 / 参照掃除 / 文字列置換）
   ▼
[公開用] iwata-jawsug-jp/devcon ＝ モノレポのゴールデンパスのテンプレート
   │  copier copy（copier.yml の _exclude / _tasks の sed）
   ▼
[生成先] 第三者のプロダクトリポジトリ
```

この2つの導線は同じ「資産を絞り込む」処理を担うが、別々に育ってきた。実際に両方を流して測定した結果
（copier 9.17.0、`main` = `ca3f546`。Markdown 相対リンクの解決可否、プレースホルダ表記の誤検出を除く）:

| ツリー                          | リンク切れ |
| ------------------------------- | ---------: |
| 開発用 `iwata-jawsug-jp/devcon`   |          0 |
| 公開用 `iwata-jawsug-jp/devcon` |          1 |
| 生成先（開発用ツリー起点）      |         57 |
| 生成先（公開用ツリー起点）      |         41 |

さらに、2つの生成先は**含まれるファイル自体が違う**（`.github/dependabot.yml` と issue テンプレート4件）。

判明した構造的な問題は次の4点。

  2軸に一般化したマーカー体系（`audience:no-publish` / `audience:no-generate`）とし、除去処理を両導線で共有する（#702）。
- **除外先参照の掃除**: `clean_excluded_doc_references()`（主題行の削除 + リンクのプレーンテキスト化）を共通関数と
  して切り出し、copier の `_tasks` からも呼ぶ。掃除対象は D1 のマニフェストから導出し、`release.md` / `proposal/`
  のハードコードをやめる（#703）。

いずれも #287 の実害（1文中の引用まで巻き込んで行が壊れた）を踏まえて育った実装であり、作り直さない。
チェックイン済みファイルに Jinja 記法を書かない制約（[ADR-0011](0011-scaffold-template-in-place.md)）は維持する
（HTML コメントは本リポジトリでは不可視で、レンダリングにも影響しない）。

### D3. 両ツリーに同じ健全性ゲートを掛け、検証経路を実使用経路に合わせる

生成物・公開物の**内部整合**を検査する共通スクリプトを設け、公開用ツリーと生成先ツリーの両方に同じ検査を
掛ける（#699）。

- **リンク切れ 0**、**分類違反 0**（D1 の宣言に反する資産が到達していないこと）。
- 判定は D1 のマニフェスト由来の**パス集合**で行う。`copier` / `scaffold` / `テンプレート` といった**語彙の
  grep はしない** —— これらは生成先でも正当に登場する（`.claude/skills/kiro-*` のプロンプト、`docs/sdd.md` 等）
  ため、誤検知で運用が破綻する。
- CI に「`publish-to-public.sh` の dry-run → その出力ツリーから `copier copy` → 健全性検査」を1本に繋いだ
  ジョブを追加する。公開導線は現在リリース時にしか走らないため、dry-run を PR ごとに回す。

### D4. ADR の分類はメタデータ行で行い、ディレクトリ分割・番号変更・本文書き換えはしない

各 ADR のヘッダに `- **Audience:**` を1行足して分類する（#704）。

却下した代替案:

- **`docs/adr/template/` へのディレクトリ分割**: ADR 番号は通番で、Accepted 後は書き換えない運用
  （[ADR-0001](0001-record-architecture-decisions.md)）。移動すると本リポジトリ側の既存リンク約30箇所の書き換えが
  発生し、履歴の追跡性が下がる。メタデータ行なら内容・パス・番号を一切動かさずに分類できる。
- **生成時の ADR 本文書き換え**（issue 番号の除去・改名履歴の現在形化）: ADR-0001 と衝突し、同じ ADR の
  2バージョンを二重管理することになる。生成先で意味を失う参照は「読み手が辿れない情報」であって「壊れた
  リンク」ではない（ADR 本文中の `#40` のような番号は Markdown ファイル内では自動リンクされない）。

### D5. 却下した構成変更

- **`template/` サブディレクトリへの分離**（生成対象を `template/` 配下に限定する案）: [ADR-0011](0011-scaffold-template-in-place.md)
  の「devcon 自身が常に動くテンプレートであり続ける」前提と正面衝突する。アプリ一式を `template/` に
  押し込むと `.devcontainer/` がリポジトリルートから消えて Dev Container が開けなくなり、`Makefile` / CI /
  Terraform の相対パスも全滅する。公開用リポジトリも「そのまま動くサンプル」であることを兼ねており、同じ
  理由で採らない。ADR-0011 の再検討トリガーは「`_exclude` の運用コストが過大と判明した場合」だが、今回の実測が
  示したのは**除外機構の粒度不足と分類軸の不在**であり、D1〜D3 で機構を揃える方が変更コストが桁違いに小さい。
- **`.copier-answers.yml` の削除**: `copier update` による下流追従（#298、[ADR-0010](0010-adopt-copier-for-scaffold-cli.md)
  で copier を選んだ決め手）に必須。削除すると生成先はテンプレートの改善を取り込めなくなる。
- **`docs/` の再編**（`architecture/` / `operations/` / `development/` 等）: 本 ADR の対象（導線を通した資産分離）
  とは独立した論点。実施するとリポジトリ全体で相対リンクの大規模改変が発生するため、D3 のリンクゲートが入って
  回帰を検出できるようになってから別途判断する（保留）。

## Consequences

**良い面**

- 「公開しないが生成する」象限が初めて表現でき、生成先の成果物が起点ツリーに依存しなくなる。
- 新規ファイル追加時の「2つの除外リストへの追記漏れ」（#515 の再発）が、単一の付け忘れ検査に集約される。
- 生成先が `infra/` や `services/` の設計根拠（ADR）を自分の中に持てる。ADR 参照のリンク切れ 32 件が解消する。
- 公開導線で実証済みの実装を共有するため、#287 と同じ失敗を繰り返さない。

**トレードオフ・新たに生じる負担**

- マニフェスト → 除外リストの codegen とドリフト検査という配管が増える。`copier.yml` / `publish-to-public.sh` を
  直接編集する運用は禁止になる。
- マーカー（`audience:no-*`）で囲む作業が、文書を書く側の新しい負担になる。囲み忘れは D3 のゲートでしか
  検出できない。
- `generate: true` の ADR から `generate: false` の ADR へのリンクが新たに切れる（実測・#704 で
  確定: ADR-0012 → 0010/0011、ADR-0027 → 0019、`infra/bootstrap/README.md` → 0011/0016、計5件。
  `0018` は `publish, generate` 両方に決まったため新規の切断は発生しない）。D2 の参照掃除
  （#703、`tools/script/clean-excluded-doc-references.sh`）の対象に自動的に含まれる（audience.yml の
  generate:false エントリから導出するため、個別対応は不要）。正味の効果は「32 件解消・5件を
  参照掃除対象に追加（掃除後はリンク切れ0件）」。

**解決済みの未決事項**

- **`_tasks` は `copier update` でも実行されるか**（#701、実機確認済み）: **される。** テンプレート側に
  検証用の `_tasks` エントリ（新規ファイル作成／既存ファイル削除の2パターン）を、同じスクラッチ
  クローンへ新しいコミットとして積み、生成済みプロジェクトに対して `copier update --vcs-ref=HEAD` を
  実行したところ、いずれも正しく再実行された。同一 ref（ドリフト無し）への update では生成物が完全に
  一致し、`_tasks`（sed による文字列置換）が冪等であることも確認した。これにより D2（マーカー除去、
  #702）・D4（テンプレート ADR 削除、#704）はいずれも `_tasks` だけで実装でき、`_migrations` の併用は
  不要と判断した。
  - **注意（独立検証で判明・要修正した設計ミス）**: 当初 `verify-scaffold.sh` の往復チェックに
    「同一 ref（ドリフト無し）update の前後でファイル一覧が完全一致すること」という検証を追加したが、
    これは `_tasks` の再実行を実際には検証できていなかった。`copier update` は内部で3-way merge を行い、
    テンプレート側に実差分が無い場合は生成済みの内容を「ローカルカスタマイズ」とみなして温存するため、
    `_tasks` を丸ごと空にしても検出できないことが判明した。正しくは実際にテンプレート側へドリフト
    （新しいコミット）を注入し、その差分が `_tasks` を通じて反映されることを検証する必要がある。
    `verify-scaffold.sh` を「同じスクラッチクローンに `_tasks` でファイルを削除するタスクを追加した
    コミットを積み、生成済みプロジェクトを update した後にそのファイルが消えていること」を検証する
    形に修正し、実際に壊れた削除タスク（存在しないファイル名を指定する等）を注入すると正しく検出して
    落ちることも確認した。
  `generate` の両方を `false` に決定した（`tools/template/audience.yml`）。`dependabot.yml` は
  本来 `generate: true` が望ましいが、実配布経路（第三者は公開用ツリー起点で `copier copy` する）
  では `publish: false` のファイルを配布できないため整合を優先した。
- **ADR-0002 / 0016 / 0018 の `Audience`（#704）**: `0016`（bootstrap の配布経路）・`0018`
  （devcontainer イメージの GHCR 事前ビルド）は他の ADR や実コードとの照合により、`0002`（SDD 採用）は
  決定内容の性質そのものにより判断した。
  - **0002（SDD 採用）**: `publish, generate` 両方。Decision 自体（上流工程への SDD 導入）は
    devcon 固有ではない一般的な開発プロセス上の判断であり、成果物（`.claude/skills/kiro-*`・
    `docs/sdd.md`）は既に既定値（両方 true）で生成先へ配布されている。
  - **0016（bootstrap の配布）**: `publish` のみ。ADR-0010/0011/0012 と同種の「テンプレート自身を
    どこに置き・どう配布するか」という運用判断であり、`infra/bootstrap/` の Terraform コード自体
    （生成先にそのままコピーされる部分）は配布方式に依存する記述を持たない。生成先が知るべき
    運用知識（公開ミラー参照のタグ運用）は `infra/bootstrap/README.md` が別途担う。
  - **0018（devcontainer GHCR 事前ビルド）**: `publish, generate` 両方。`cacheFrom` の値
    （`ghcr.io/iwata-jawsug-jp/devcon/...`）は `_tasks` の文字列置換対象に含まれず生成先にも
    そのまま出力されるため、「なぜ他組織の GHCR パスが残っているか」を理解する当事者向けの
    設計判断として生成先の利用者にも必要と判断した。
  - **副次的な発見（未解決のまま残す）**: `0002` の判断過程で、`.kiro/steering/`（`product.md` 等）が
    現状 `tools/template/audience.yml` に個別エントリを持たず既定の `generate: true` のまま
    生成先へ配布されており、`product.md` は実際に devcon 固有の記述（JAWS-UG 磐田コミュニティ
    向け、との説明等）を含むことを確認した。ADR-0011 が「要検討」としていた懸念がデータでも
    裏付けられた形だが、`0002` 自身の `Audience` 判断はこれに依存しないため、`.kiro/steering/` 自体の
    分類は本 issue のスコープ外とし、別途 issue を立てて対応する。

**再検討トリガー**

- マニフェスト + codegen の運用コストが、2リスト個別管理より明らかに高いと実装を通じて分かった場合、
  D1 の導出方式（単一の正）を再検討する。
- 生成先と公開用リポジトリで必要な構造が本質的に乖離し、マーカーとマニフェストでは表現しきれなくなった場合、
  D5 で却下した `template/` 分離（ADR-0011 の再検討）に戻る。
